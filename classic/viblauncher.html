Release notes

Fetching the latest release notes.

Vib-launcher is a native Windows Minecraft launcher and vib-MC server control panel. It manages isolated Minecraft instances, Microsoft and offline accounts, mod loaders, mods from Modrinth, and local vib-MC servers, in one desktop application wearing the Vib Studios Classic theme.

It is a real WPF application. There is no browser, no WebView and no embedded web page anywhere in it. Nothing from Minecraft is bundled either: client jars, libraries and assets are fetched from Mojang's own distribution endpoints and verified against the hashes Mojang publishes with them. Everything below comes from the repository README, without a marketing layer on top, so where something does not work yet this page says so.

[edit] Overview

The launcher does three separate jobs from one window: it keeps Minecraft instances apart from each other, it signs accounts in, and it runs vib-MC servers on the same machine. Instances and servers never share a directory, because a client and a server want different things from a folder.

What works

Instances
Created, launched, imported and exported, each in its own folder, with versions, libraries and assets shared between them.
Accounts
Microsoft sign in over the device code flow, and offline profiles that keep their player data across launches.
Mod loaders
Fabric and Quilt install completely. Forge and NeoForge are listed but not installed.
Mods
Searched and installed from Modrinth, filtered to what the instance can actually run, with required dependencies resolved.
vib-MC servers
Downloaded, started, watched through a console, backed up, updated and edited, without the launcher ever hosting the server process inside itself.
Downloads
Queued with progress, retried on failure, cancellable, and every file checked against the hash published with it.

What does not

Stated plainly rather than hidden behind a disabled button.

  • Forge and NeoForge cannot be installed. Their real published builds are listed, and the Create Instance dialog explains the limitation instead of making an instance that would not start. Fabric and Quilt are complete.
  • Microsoft sign in needs a client id supplied by whoever ships the build. The full auth chain is implemented and works once one is configured. Offline accounts need nothing.
  • No managed Java downloads. The launcher finds installed runtimes and names the release a version needs, but does not fetch one for you.
  • CurseForge packs are not imported, and CurseForge is not a mod source. That format names its mods by project id, which needs an API key this launcher does not ship.
  • Server plugin management is not implemented. Servers get a plugins/ folder and a button that opens it.
  • Player counts and server memory use are not shown, because nothing available reports them reliably. The fields show what is known rather than invented numbers.
  • Windows only. WPF is a Windows toolkit, and the launcher uses DPAPI and a DWM call besides.

First run

The release is a zip holding a single VibLauncher.exe. Unzip it anywhere and run it. There is no installer and nothing is written outside %APPDATA%\VibLauncher. Windows SmartScreen will warn about an unsigned executable, because it is unsigned.

On a first start there are no instances and no accounts. Add an account first, offline or Microsoft, then create an instance: pick a Minecraft version, pick a loader, and the launcher downloads what that combination needs and verifies each file as it arrives.

Building from source

Two commands, with the .NET 10 SDK installed.

Terminal 
$ dotnet build -c Release
$ dotnet run --project src/VibLauncher.App

dotnet test runs 208 tests covering instance and account persistence, import and export, mod compatibility and enable or disable, download success, checksum failure, retry and cancellation, server.properties round-tripping, port probing, version metadata parsing and merging, argument building, path safety and credential redaction. None of them need a network: the download tests stand up a loopback HTTP server.

[edit] Instances

An instance is one folder under instances/ holding the launcher's record, the mods it installed, its own extracted natives and its own .minecraft game directory. Versions, libraries and assets live outside it and are shared, so a second instance on a version already installed costs almost nothing on disk. Only the game directory and the natives are per instance.

The record is instance.json, readable and hand editable: 

{
  "id": "fabric-survival",
  "name": "Fabric Survival",
  "minecraftVersion": "1.21.8",
  "loader": "fabric",
  "loaderVersion": "0.17.2",
  "launchVersionId": "fabric-loader-0.17.2-1.21.8",
  "javaPath": null,
  "minMemoryMb": 1024,
  "maxMemoryMb": 6144,
  "jvmArguments": "-XX:+UseG1GC"
}

launchVersionId is what actually gets launched. For Vanilla it equals minecraftVersion; installing a loader replaces it with the loader's own profile id.

Exporting and importing

An export is a .vibinstance zip holding that record plus the mods, config, resource packs, shader packs and worlds. Assets, libraries, versions, logs and crash reports are left out: they are redownloadable, and bundling Mojang's files into a shareable archive is not something the launcher does.

Export opens a picker first. It shows everything the archive would carry as a tree with a size against each branch, and unticking a folder or a single file leaves it out. Nothing on disk is touched: the instance is unchanged, only the archive is smaller. A folder with some of its files unticked shows a half tick, so what the archive holds is readable without opening every branch.

Import accepts three shapes, told apart by what is inside the file rather than by its extension.

Import formats as of v0.1.1.
Shape Recognised by What happens
.vibinstance vibinstance.json The record and files are restored, and the mod loader it names is installed.
.mrpack modrinth.index.json Version and loader come from the pack's dependencies, overrides are unpacked, and every file the index lists is downloaded from its published address and checked against its published SHA-1. Files marked client unsupported are skipped.
plain .zip a .minecraft folder, or one holding mods, config, saves or options.txt The game folder is unpacked. An instance.json beside it is honoured; without one the launcher asks for a version rather than guessing.
CurseForge pack its own manifest Refused with an explanation. Resolving its mods needs the CurseForge API, which this launcher does not ship a key for.

An archive re-zipped inside a wrapper folder is still read correctly: the format's root is found at whatever depth it sits at. Every entry name is resolved under the destination before anything is written, so an archive cannot place a file outside the instance it is being imported into, and the same check applies to the paths in a modpack's index. An import that fails part way through, including a modpack whose downloads do not complete, leaves nothing behind.

[edit] Accounts

Microsoft accounts use the device code flow: Microsoft identity, then Xbox Live, then XSTS, then Minecraft services. The launcher never sees a Microsoft password. It shows a code, the person signs in on Microsoft's own page, and the launcher polls until it is done.

accounts.json holds only names, UUIDs and expiry times. Tokens go to a separate store encrypted with DPAPI under the current Windows user, and every log line passes through a redaction filter on the way out, so a token cannot reach a log even inside an exception message.

Offline accounts derive the same UUID a server computes for an unauthenticated player: a version 3 UUID over OfflinePlayer:<name>. A local profile therefore keeps its player data across launches, and matches what a vib-MC server with online-mode=false hands out.

Microsoft sign in needs an Azure application id, and one is deliberately not compiled in. A client id is public rather than secret, but it belongs to whoever ships a build. Set it in Settings, or in the VIBLAUNCHER_MSA_CLIENT_ID environment variable. The window says so rather than offering a button that would fail.

[edit] Mod loaders and mods

Loader support as of v0.1.1.
Loader Lists versions Installs
Vanilla not applicable not applicable
Fabric Yes Yes
Quilt Yes Yes
NeoForge Yes No
Forge Yes No

Fabric and Quilt install completely: their metadata services publish a ready made version profile, which the launcher writes into the versions folder and merges over the vanilla version at launch. Forge and NeoForge install by running their own installer jar, which patches the client and writes a profile, so their real published builds are listed and the install is refused with a reason rather than producing an instance that does not start.

Mods come from Modrinth, through its documented v2 API. No page is scraped and no key is required. Compatibility is a property of the query rather than an afterthought: the search is filtered by the instance's Minecraft version and loader before it leaves the launcher, so every result shown is installable. The specific file is checked again at install time, and a mismatch is refused with both sides named: 

"Sodium 0.5.8" cannot be installed into "Fabric Survival".

That release supports Minecraft 1.20.1 on fabric. This instance is
Minecraft 1.21.8 on Fabric. Pick a different release, or change the
instance's version.

Required dependencies are resolved automatically, depth limited against cycles, and anything that could not be satisfied is reported rather than silently skipped. Disabling a mod renames it to .jar.disabled, which every loader ignores. Nothing is deleted, so re-enabling is exact.

[edit] vib-MC servers

Servers are a separate concept from instances and never share a directory. An instance is a client the launcher starts; a server is a Java process that listens on a port and owns its own worlds. Jars come from the vib-MC project's GitHub releases: this website is where a person reads about that project, and the launcher goes to the API for a jar and builds its own native window around it.

The process
A child process with its streams redirected, never inside the launcher, so a server crash cannot take the launcher down. Output feeds the console view and a per run log file, typed commands go to stdin, and a crash is reported with its exit code and a route to the log. Nothing is auto restarted.
Ports
Checked before a start, and a conflict offers the next free port. The port is never changed for you: a server that silently moves is a server nobody can connect to.
Updates
Only the jar is replaced, after a backup is taken. Worlds, player data, plugins and server.properties are never touched.
Backups
Kept outside the server folder, so deleting a server does not delete them, and a restore archives the current worlds before overwriting them.
server.properties
Edited with comments, key order and unknown keys preserved, because that file is one a server owner is likely to have edited by hand. Settings that only take effect on a rebind are labelled as needing a restart.

[edit] Where things are kept

Everything lives under %APPDATA%\VibLauncher.

VibLauncher
├─ launcher-data/       settings, accounts, tokens, cached metadata, logs
├─ instances/<id>/      one folder per instance
│  ├─ instance.json     the launcher's record
│  ├─ mods.json         where each installed mod came from
│  ├─ natives/          extracted per instance, so versions cannot clash
│  ├─ logs/             stdout and stderr, one file per launch
│  └─ .minecraft/       mods, config, saves, screenshots
├─ servers/<id>/        one folder per vib-MC server
│  └─ console-logs/     console output, one file per run
├─ minecraft/           versions, libraries and assets, shared
├─ backups/<id>/        world backups, deliberately outside the server
└─ downloads/

No path is built by hand anywhere in the code. Everything goes through ILauncherPaths, so moving the data root is a one line change.

[edit] Architecture 

VibLauncher.App              WPF. Views, view models, theme. No launcher logic.
      │
      ├── VibLauncher.Core   The domain and its rules. No network, no UI,
      │                      no Windows APIs.
      │
      └── VibLauncher.Infrastructure
                             Where Core's interfaces meet the outside world.

Core defines the interfaces, Infrastructure implements them, and the App composes them once in LauncherServices and hands them to view models. Core references neither of the others, which is what lets the rules be tested without a network or a window.

Adding a loader means implementing ILoaderProvider and adding it to the list in LauncherServices. Adding a mod source means implementing IModProvider the same way. A provider that needs credentials reports itself unavailable with a reason until it has them, and the window hides it instead of failing a search.

[edit] The Classic theme

The palette, type and shapes come from the classic vib-MC layout, whose tokens are authored in oklch and converted to sRGB in the theme, with the originals kept in comments.

void-900oklch(17% .02 40)#170C09card

ember-500oklch(64% .19 40)#E65719pressed

Every WPF control is retemplated, because the stock chrome is light themed and rounded in a different idiom. Icons are vector paths on a 16 unit grid, never an icon font and never emoji, so nothing depends on a typeface being installed. The title bar is darkened through DWM so it matches the window.

One deliberate departure from the website: its buttons are pills, which read as a web control on the desktop, so buttons in the launcher use the same 6px radius as the inputs beside them.
